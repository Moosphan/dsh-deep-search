# 性能优化评估

基于本机现有缓存与代码路径的实测/代码审查，不含会话内容。

## 现状

| 指标 | 数值 |
| --- | --- |
| 逻辑会话 | 71 |
| 可检索文本 | 约 153 MB |
| 缓存体积 | 约 23 MB（gzip） |
| 最大单会话 | 约 1,050 万字符 |
| 冷构建 | 约 130 s（优化前） |
| 缓存加载 | 约 163 ms（71 个缓存文件） |
| 暖缓存首次检索 | 约 648 ms（含缓存加载与 facets） |
| 纯检索耗时 | 约 36 ms（扫描 113,953 段，命中 1,205） |

## 主要瓶颈

### 1. live 会话整段重解析（最高优先级）

修订号是 `live:事件数`。当前会话一旦新增事件，整个会话都会失效并重新 parse。一个 1,050 万字符的 live 会话反复重读，是后台刷新和冷构建的主要成本。

建议：缓存 `lastSeq` 与文档游标，只追加解析新事件；遇到历史事件被修改时再回退到全量重建。收益最大，复杂度中等。

### 2. 解析与压缩占用 Host 主线程

JSONL 解析、文档抽取、gzip 压缩都在 Host 主线程执行。`setImmediate` 只是让出事件循环，CPU 仍与 HTTP、会话写入竞争。

建议：用 `worker_threads` 池处理解压、JSONL 解析与缓存压缩；主线程只接收紧凑的 docs 结果。缓存压缩可改为异步或在空闲时执行。

### 3. 检索仍是全量线性扫描

每次查询遍历所有会话的所有 docs，逐段执行匹配。当前 11 万段 36 ms 可接受，但到百万段会线性恶化；正则查询无法利用标题/路径的短路径。

建议：为字面量关键词建立 CJK bigram + ASCII token 倒排索引，标题/路径单独加权；正则保留线性回退。索引可持久化，和缓存一起加载。

### 4. 冷启动必须等全量完成

空缓存时所有会话串行解析，面板只能等整库完成。即使已有缓存，后台刷新也会重新解析变更会话。

建议：先索引最近 200 个会话并标记 `partial`，面板立即可搜；其余会话后台补齐，结果按需合并。与增量解析配合收益最好。

### 5. 客户端一次性渲染全部命中

最多 48 组 × 30 条 = 1,440 行 DOM，流式追加时可能造成长列表卡顿。

建议：列表虚拟化（windowing），只渲染视口附近；保留当前选中/滚动恢复逻辑。已有 AbortController 和 130ms 防抖，不需要重做请求层。

### 6. 缓存是单会话大 JSON

单会话一个完整 JSON，10M 字符会话的 `JSON.parse/stringify` 和大块 gzip 都会产生长任务。

建议：按 turn/block 分块缓存，或采用 append-only 段文件；加载时只解析需要的块。可与增量解析合并设计。

## 优先级

| 优先级 | 优化 | 预期收益 | 成本 |
| --- | --- | --- | --- |
| P0 | live 会话增量解析（lastSeq） | 消除反复 130s 级重解析 | 中 |
| P0 | Worker 线程解析/压缩 | Host 不再被解析阻塞 | 中高 |
| P1 | 最近会话优先的 partial index | 冷启动首屏从分钟级到秒级 | 中 |
| P1 | 关键词倒排索引 | 百万段仍保持低延迟 | 高 |
| P2 | 结果列表虚拟化 | 长列表滚动/流式追加不卡 | 低 |
| P2 | 查询结果缓存 + 索引版本键 | 重复查询近零成本 | 低 |
| P2 | 缓存分块/异步压缩 | 降低大会话长任务 | 中 |

## 建议顺序

1. **先做 live 会话增量解析**：直接消掉最常见的重复成本。
2. **再把解析/压缩移入 worker**：解决 Host 卡顿，保留现有 API。
3. **随后做 recent-first partial index**：改善冷启动体验。
4. **最后再考虑倒排索引**：当前 11 万段 36 ms 尚可，等语料再上一个量级再做。
