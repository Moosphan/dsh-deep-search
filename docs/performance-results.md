# 性能优化结果（1.1.0）

## 基准方法

使用可重复的合成语料，避免依赖真实会话内容：

- 61 个会话：1 个 200,000 事件的超大会话，60 个 150 事件的近期会话。
- 大会话故意排在列表第一位，模拟最坏的冷启动顺序。
- 查询 `needle`，统计首屏返回、建索引完成时间。
- 解析基准：60,000 个事件的单会话；增量场景追加 2 个事件。
- 环境：Apple Silicon / Node.js 24；暖缓存数据取 3 次运行中位数。

## 优化前 vs 优化后

| 指标 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 单会话全量解析（60k 事件） | 约 170 ms | 约 15 ms（增量追加 2 事件） | **约 91% 降低** |
| 冷启动首屏（最坏顺序） | 705 ms / 1 组 / 200k 候选 | 49 ms / 14 组 / 2.1k 候选 | **约 14× 更快** |
| 冷启动建完 61 会话 | 950 ms | 831 ms | 约 13% 降低 |
| 暖缓存首次检索（合成 61 会话） | 约 309 ms | 约 261 ms | 约 16% 降低 |
| 暖缓存加载（真实 71 会话） | 约 163 ms | 约 163 ms | 持平 |
| 单次查询扫描（真实 113,953 段） | 约 36 ms | 约 36 ms | 持平（未做倒排索引） |

## 本版实际改动

1. **live 会话增量解析**：缓存 `lastSeq`、turn/step 与 toolNames；只解析序号大于游标的新事件。遇到序号回退自动全量重建。
2. **冷启动 recent-first**：按 `updatedAt` 排序，先索引最近会话；首屏在 49 ms 返回 14 组近期结果，不再被超大会话堵住。
3. **异步缓存压缩**：gzip 压缩移出同步路径；缓存解压保留同步快路径。
4. **回归测试**：新增“增量解析结果必须与全量解析一致”测试，当前 18 项全部通过。

## 尚未完成

- Worker 线程解析/压缩：主线程仍承担 JSONL 解析 CPU。
- 关键词倒排索引：查询仍是全量线性扫描，36 ms 在当前语料可接受，百万段后需要。
- 结果列表虚拟化：长列表 DOM 仍一次性渲染。

## 结论

本版主要解决的是**冷启动首屏**和**live 会话重复解析**，不是查询吞吐。真实生产环境的暖缓存首屏此前约 648 ms（含缓存加载与 facets），查询本身约 36 ms；1.1.0 的增量解析会在后续 live 刷新中持续生效。
