# 极致性能路线

## 当前瓶颈（1.4.0 实测）

| 环节 | 当前 | 原因 |
| --- | --- | --- |
| 真实冷建（71 会话 / 153 MB） | ~130 s | 首次全量读取 + 解压 + 解析所有会话 |
| 真实暖缓存首屏 | 641–699 ms | 71 个缓存文件的 JSON 解析 + facets |
| 查询扫描 | 32 ms / 113,953 段 | 每个查询线性遍历所有 docs |
| 内存 | 约 153 MB 文本 + docs | 全量索引常驻内存 |
| live 增量写入 | 0.4 ms / 313 B | 已用 delta 分块，接近最优 |

目标不是“再快一点”，而是换掉线性扫描与全量常驻：

- 冷启动首屏 < 100 ms；
- 暖缓存首屏 < 100 ms；
- 查询 p95 < 10 ms（百万段落）；
- live 更新 < 5 ms；
- 内存 < 100 MB。

## 核心方案：SQLite FTS5 磁盘索引

把“内存 docs + JSON 缓存”换成 **SQLite FTS5**：

```
sessions(id, cwd, title, created_at, updated_at, last_seq, ...)
docs(id, session_id, kind, role, turn, seq, ts, text, ext, call, ...)
docs_fts(text, content='docs', tokenize='trigram' 或 bigram)
```

- 查询走 `MATCH` + BM25，不再扫描全部 docs。
- 时间、工作空间、位置、文件类型直接 SQL 过滤。
- 分页/排序/高亮由 FTS5 完成，结果集小。
- 索引落盘，进程启动只打开 DB，不再加载 153 MB 文本。
- 增量写入是事务 upsert，天然支持 delta/compaction。
- 本地优先不变：单文件 DB，无网络。

### 中文分词

FTS5 的 `unicode61` 不切中文。两条路线：

1. `tokenize='trigram'`：直接支持中文子串（3 字以上），2 字查询回退 `LIKE` 或 bigram 列；
2. 自建 **bigram 列**：把中文文本切成双字 token，查询同样切分，精确且召回可控。

推荐 bigram + ASCII token，trigram 作为兜底。

## 按需回填，而不是全量冷建

- 启动只打开 DB，并确保最近 N 个会话已入库（例如 200）。
- 其余会话进入后台队列，按 `updatedAt` 从近到远回填。
- 搜索默认覆盖已入库会话；UI 显示“正在补齐旧会话”，回填后结果自动刷新。
- 首次安装不再等 130 s；用户 100 ms 内可搜索最近历史。
- 冷建从“阻塞启动”变成“持续后台任务”。

## 直接读日志的 Worker

上次 Worker 失败的原因是把完整 `events` 数组 structured clone 到 worker；clone 成本超过了并行收益（冷建 831 → 2,171 ms）。

正确做法：

- Worker 接收 **会话日志路径 + 修订号**，不接收 events；
- 在 worker 内直接 `zstd` 解压 + JSONL 流式解析；
- 只把紧凑 docs 回传主线程（或直接写 SQLite）；
- 2–4 个 worker 并行处理不同会话，主线程只做调度和 DB 写入。

这需要 DSH 暴露会话文件路径（或插件从 `~/.dsh/sessions` 解析），但能真正利用多核，且不再 clone 大对象。

## 查询层

1. 字面量：FTS5 MATCH + BM25 + 标题/路径加权；
2. 正则：SQL 预过滤（时间/工作空间/类型）后，对候选集做 `RegExp`；仍设 3.2 s 截止；
3. 结果缓存：查询 + 筛选 + DB revision 作为 key，TTL 15 s；
4. 分页：`LIMIT/OFFSET` 或游标，客户端虚拟列表；
5. `snippet()`/`highlight()` 由 FTS5 生成，减少 JS 高亮成本。

## 客户端

- 列表虚拟化（windowing），只渲染视口附近 100–200 行；
- 流式结果按页追加，服务端限制单页 50 组；
- 预取下一组会话；保持选中/滚动恢复。

## 分阶段落地

| 阶段 | 内容 | 预期 |
| --- | --- | --- |
| P0 | SQLite FTS5 + 最近 200 会话按需回填 | 冷启动首屏 < 100 ms；查询 < 10 ms |
| P1 | Worker 直接读日志 + 并行入库 | 全量回填从分钟级降到十秒级 |
| P2 | 客户端虚拟化 + 服务端分页 | 大结果集滚动稳定 |
| P3 | 可选 Rust/Tantivy 原生索引 | 千万段落级；代价是跨平台构建 |

## 风险与取舍

- **原生依赖**：`better-sqlite3` 需要跨平台预编译；若 DSH 运行时提供 `node:sqlite`，优先内置模块，免原生依赖。
- **迁移**：现有 JSON/delta 缓存需要一次性迁移到 DB；保留旧缓存回退，失败可重建。
- **中文分词**：bigram 召回高但索引大；trigram 索引小但 2 字查询需回退。
- **隐私**：DB 仍只存本地，权限 0700/0600；删除 DB 即清空。
- **插件市场**：原生依赖会影响打包；这是 P0 前必须确认的约束。

## 结论

继续在现有 JSON 缓存上做微优化，收益已经接近上限。要达到极致，应该把索引层换成 **SQLite FTS5 的磁盘倒排索引**，配合 **按需回填** 和 **直接读日志的 Worker**。这三件事分别解决：查询线性扫描、冷启动 130 s、主线程解析。
